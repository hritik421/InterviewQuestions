4. Interview Q&A
Q1: "Why did you choose the BFF pattern instead of calling backend services directly from the browser?"
A: We implemented the BFF pattern specifically to solve a distributed tracing problem. New Relic's browser agent auto-injects traceparent headers, but only for same-origin requests. When the browser called backend services directly (cross-origin), the trace chain broke — we couldn't correlate frontend user actions with backend service calls. By routing all API calls through Next.js API routes on the same origin, the traceparent header propagates end-to-end. This also gave us security benefits — backend service URLs are hidden from the browser, and we can add server-side caching or request transformation in the BFF without touching frontend code. The implementation uses a BFFConfigInterceptor that monkey-patches window.fetch() to transparently rewrite external URLs to BFF paths, so existing service layer code required zero changes.

Q2: "How did you handle micro-frontend integration with the product selection widget?"
A: The product hierarchy selection is owned by a separate team, so we integrated their product-dimension-selection-widget as a Web Component. This gives us framework isolation — their widget can be built with any technology and deployed independently with its own version lifecycle. Communication happens through an EventBus pattern using the aprie-widget-communication-library. When a user selects products in the widget, it fires events that our ProductForm component listens to, then we persist selections through our UserPreferencesService. The challenge was state synchronization — we needed to ensure the widget's internal state stayed consistent with our React context. We solved this by treating the widget as a controlled component, passing initial state via attributes and handling all persistence in the host application.

Q3: "How did you ensure API compatibility across 7+ backend services with separate teams?"
A: We implemented consumer-driven contract testing using Pact. We have 9 pact contracts covering all our backend integrations. Our frontend defines the expected API behavior in pact files — what request we send and what response we expect. These contracts are published to a Pact Broker, and backend teams validate their services against our contracts in their CI pipelines. This catches breaking changes before they reach any shared environment. For example, if the Onboarding Service team changes a response field name, their build fails against our contract, and they know to coordinate the change. Combined with our Jest unit tests (46+ specs), Playwright E2E tests, and SonarQube quality gates, we maintained high confidence in releases despite coordinating with multiple teams.

Q4: "Walk me through how you handled multi-tenancy and internationalization."
A: Multi-tenancy is handled at the build level — we have separate build variants for Walmart, default, and default-mr tenants. Each variant has tenant-specific configurations, branding, and feature flags. At deployment time, Helm values inject tenant-specific environment variables. For internationalization, we use i18next with a lazy-loading strategy. Translations are organized as locales/[language]/translations.json for base translations and locales/[language]/translations-[marketCode].json for market-specific overrides. Legal policies are versioned (1.0.0 through 3.1.0) with localized content stored in the public directory. The useTranslatePolicyName hook handles runtime policy name translation. This architecture allows us to onboard a new market by adding a translation file and a build variant — no code changes required.

Q5: "What was your deployment strategy and how did you handle zero-downtime releases?"
A: We deploy to Kubernetes clusters on both GCP (GKE) and Azure (AKS) using Helm and Helmfile. For zero-downtime releases, we use ArgoRollouts with canary deployment strategy — new versions are gradually rolled out to a percentage of traffic while monitoring New Relic metrics for error rates and latency. If metrics degrade, the rollout automatically pauses. Pod topology spread constraints ensure zone-redundant distribution across availability zones. The Istio service mesh handles mTLS between services and manages cross-namespace traffic policies — our frontend pods in the dhsmart-* namespace need to reach the Product Universe Gateway in the polaris-* namespace, which requires explicit AuthorizationPolicy configuration. The entire pipeline is automated through GitLab CI with build, test (lint + unit + contract + E2E), Docker image build, and Helm deployment stages.
